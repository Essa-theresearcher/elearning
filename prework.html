Spend six hours proving real readiness

This Week 1 intensive checks whether the student can think and work like an intermediate beginner before entering Lesson 1.

A student may say they are intermediate, but the useful question is whether they can explain their thinking, debug small problems, use data structures, and ship a small working result without being carried by step-by-step instructions.

This 6-hour readiness intensive is not meant to punish anyone. It helps you place the student correctly. Strong students move into Lesson 1 with confidence. Students with gaps get a clear map of what to review.

Lesson 1 unlocks only after this Week 1 page is completed, the diagnostic quiz is submitted, and the mini project is submitted.

What you are looking for

  • Can they explain code instead of only copying it?
  • Can they use variables, loops, functions, lists, dictionaries, and conditionals?
  • Can they read an error message and make a reasonable debugging attempt?
  • Can they organize a tiny project and describe tradeoffs?

Reading

The detailed intermediate readiness standard

This is the main 2-hour reading and practice block. It defines what "intermediate" means for this course.

1. Intermediate means you can reason, not just remember

In this course, an intermediate student does not need to know every library or every shortcut. They do need to understand how a small program moves from input to processing to output. If they see a block of code, they should be able to say what each part is responsible for.

A useful test is this: can the student change a working example without breaking the whole thing? If the answer is yes, they are probably ready for faster lessons. If every small change feels mysterious, the student needs more practice with fundamentals.

2. The baseline toolkit

An intermediate beginner should be comfortable with:

  • Variables, strings, numbers, booleans, and basic type conversion.
  • Conditionals such as if, elif, and else.
  • Loops over lists, strings, or dictionary items.
  • Functions that accept inputs, return values, and avoid repeated code.
  • Lists and dictionaries for organizing related data.
  • Reading error messages and testing one small fix at a time.

3. Debugging is part of the assessment

The mini project is allowed to contain mistakes while it is being built. What matters is whether the student can isolate the problem. Good debugging sounds like: "This function receives a list, but I passed a string" or "The loop works, but my condition is too broad."

Weak debugging sounds like: "It does not work" with no attempt to locate where. The course will teach deeper ideas, but the student needs enough patience and structure to investigate small failures.

4. What to do with the result

Use the quiz and project together. A high quiz score with a weak project may mean the student recognizes concepts but cannot apply them yet. A modest quiz score with a strong project may mean the student can build but needs vocabulary review. The project reflection is important because it shows how the student thinks. 

Readiness decision:
- Ready: quiz is solid, project runs, explanation is clear.
- Almost ready: project is incomplete but reasoning is visible.
- Needs foundations: cannot explain code, no working project, or no debugging evidence.

5. Six-hour work plan

The student should not rush this in ten minutes. The point is to observe stamina, independence, and problem-solving habits. A student who is ready for the course should be able to keep working through a structured technical task for several hours without needing every move dictated.

  • 20 minutes: read the welcome, rate confidence, and write down what "intermediate" means to them.
  • 120 minutes: read the standards, review examples, and write small practice snippets for loops, functions, lists, and dictionaries.
  • 45 minutes: take the diagnostic quiz, review missed categories, and retake only after noting why each mistake happened.
  • 150 minutes: build the mini project, test it with at least three different learner profiles, and improve the output.
  • 25 minutes: submit the reflection and decide whether the evidence says ready, almost ready, or needs foundations.

6. Practice drills before the quiz

Before opening the quiz, the student should complete these short drills in their own editor or notebook:

  • Create a dictionary for a learner profile with name, goal, claimed level, and weekly study hours.
  • Create a list of five skills and loop through it to print one review sentence per skill.
  • Write a function named readiness_label that accepts a score and returns ready, almost ready, or needs foundations.
  • Intentionally break the function once, read the error message, and write one sentence explaining the fix.
  • Explain why a dictionary is better than five separate variables for storing related learner data.

Decision

Decide the student placement

Use the evidence from the week to decide whether the student should move forward, review basics, or receive a short bridge task.

Placement rubric

  • Ready for Lesson 1: completes the quiz, submits a working project, and can explain choices in plain language.
  • Almost ready: understands most ideas but needs one focused review on functions, loops, dictionaries, or debugging.
  • Needs foundations: cannot submit a working attempt or cannot explain what the code is doing.
