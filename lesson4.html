    Welcome and framing

    How Web Applications Actually Work

    How the browser, frontend, backend, database, hosting, and security fit together.

    You have now looked inside the computer, the internet, and the database. This lesson puts the pieces together into the full web app architecture students will meet in real projects.

    • Explain the roles of frontend, backend, database, and hosting in one app.
    • Trace a user action from button click to API request to database result.
    • Distinguish static websites from dynamic web applications.
    • Describe authentication, sessions, cookies, and authorization in simple terms.
    • Explain why environment variables, logs, and deployment settings matter.
    • Read a basic production architecture and identify where failures can happen.
    Time Segment Focus
    5 min Welcome and framing From separate concepts to one complete app.
    20 min Frontend and user actions HTML, CSS, JavaScript, forms, and browser events.
    20 min Backend and APIs Routes, request handlers, validation, and responses.
    20 min Database integration How the backend reads and writes saved state.
    15 min Login and permissions Authentication, sessions, cookies, roles, and access.
    15 min Deployment and environment Domains, reverse proxies, ports, logs, and environment variables.
    15 min Wrap-up and Q&A Full app trace and project preparation.

    1. Static Site vs. Web Application

    A static site mostly sends files to the browser. A web application responds to users, talks to a backend, saves data, and changes based on who is signed in.

    Concept Meaning
    Static site Same files for everyone.
    Dynamic app Responses can depend on user, data, and permissions.
    Backend The server-side program that decides what happens. 
    Browser -> HTML/CSS/JS
Browser -> API -> Database -> API response

    2. Frontend: What the User Touches

    The frontend is the part in the browser: pages, forms, buttons, layouts, and JavaScript that reacts to clicks. It should be clear, fast, and hard to misuse.

    Concept Meaning
    HTML Structure and content.
    CSS Layout and appearance.
    JavaScript Interaction and data requests. 
    button click -> collect form values -> fetch("/api/checkout")

    3. Backend: The App Brain

    The backend receives requests, checks data, applies rules, talks to the database, and sends a response. It is where trusted decisions must happen.

    Concept Meaning
    Route The URL path handled by the server.
    Validation Checking data before trusting it.
    Response What the server sends back. 
    POST /api/auth/login
GET /api/progress
POST /api/progress/quiz

    4. Database: The App Memory

    The backend should save important state in the database: users, enrollments, lesson progress, quiz results, orders, and resources. The browser alone is not enough for teacher/admin visibility.

    Concept Meaning
    User table Who can sign in.
    Enrollment table Who has access.
    Progress table What the student completed. 
    app_users -> course_enrollments -> lesson_progress

    5. Login, Sessions, and Roles

    Authentication proves who someone is. A session keeps them signed in. Authorization decides what that person is allowed to do.

    Concept Meaning
    Authentication Are you really this user?
    Session cookie Browser proof of a signed-in session.
    Role Student, teacher, or admin permissions. 
    student: view lessons
teacher: add resources
admin: approve students

    6. Deployment: Making It Live

    Production adds another layer: a domain points to the VPS, a reverse proxy routes the domain to the right app port, environment variables configure secrets, and logs tell you what broke.

    Concept Meaning
    Domain Human-friendly name.
    Reverse proxy Routes web traffic to the right app.
    Environment variable Configuration outside the code. 
    digitalbrigdeacademy.com -> Traefik -> Learning MS :8765
