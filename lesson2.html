    How the Internet Actually Works

    What really happens between typing a URL and a page loading on your screen.

    Last lesson, we went inside one machine. This lesson zooms out to what happens when that machine talks to another one anywhere in the world, usually in under a second.

    • What happens step by step between typing a URL and seeing a page load.
    • How a domain name like google.com becomes an IP address a computer can connect to.
    • What HTTP requests and responses contain, including common status codes.
    • Why internet data travels in packets instead of as one big chunk.
    • What servers, ports, APIs, and webhooks really are underneath the terms.
    • What HTTPS protects, why the TLS handshake matters, and where the padlock still has limits.

    1. Names vs. Addresses: IP Addresses and DNS

    Computers use numerical addresses to find each other. Humans use names. DNS is the system that turns a domain like google.com into an IP address that a browser can actually connect to.

    Step What happens
    Device asks Your browser asks a DNS resolver for the address behind a domain name.
    Cache check The resolver answers quickly if it has seen that domain recently.
    Root and TLD If not cached, servers point the resolver closer to the authoritative answer.
    Connection Once the browser has an IP address, it can open a connection to the server. 
    $ nslookup google.com

>>> import socket
>>> socket.gethostbyname('google.com')

    2. The Request-Response Cycle

    HTTP is the shared language browsers and servers use. The client asks for something, and the server answers with a status code, headers, and a body.

    Code Meaning What it tells you
    200 OK The request succeeded.
    301 / 302 Redirect The resource moved somewhere else.
    404 Not Found The server exists, but that path does not.
    401 / 403 Unauthorized / Forbidden You need to log in, or you are not allowed.
    500 Server Error Something broke on the server side. 
    >>> import requests
>>> response = requests.get('https://api.github.com')
>>> response.status_code
200
>>> response.headers['content-type']

    3. Data Travels in Packets

    Your data does not travel as one continuous stream. It is split into packets, routed across machines, and reassembled when it arrives.

    TCP UDP
    Delivery Reliable, confirms packets arrive. Best effort, no confirmation.
    Order Guaranteed. Not guaranteed.
    Used for Web pages, APIs, downloads. Video calls and live streaming. 
    $ traceroute google.com
# Windows: tracert google.com

    4. Servers, Ports, and APIs

    A server is a program listening for incoming requests. A port is the specific door that request goes through. APIs use the same request-response model, but return data for programs instead of pages for humans.

    • Port 80: standard plain HTTP traffic.
    • Port 443: standard HTTPS traffic.
    • Webhook: an API call triggered by an event, such as a payment confirmation.
    $ lsof -i -P | grep LISTEN
python3   ... TCP *:8000 (LISTEN)
node      ... TCP *:3000 (LISTEN)

    5. HTTPS and Encryption

    HTTPS adds encryption so packets are unreadable to machines they pass through. Before the real HTTP request is sent, the browser and server perform a TLS handshake to agree on secure communication.

    Practical rule: Never enter passwords or payment details on a page that is not using HTTPS. Payment integrations require HTTPS because sensitive data must be encrypted in transit.

    6. The Full Journey

    You type a URL -> DNS translates the domain to an IP address -> the browser connects to the right port -> HTTPS performs a TLS handshake if needed -> the browser sends an HTTP request as packets -> routers move those packets -> the server replies -> the browser reassembles and renders the page.

    Use the homework to make the internet journey explainable in your own words.

    1. Run nslookup or socket.gethostbyname() on three websites and note the IP addresses.
    2. Run requests.get() against a public API and print the status code plus one field from the response.
    3. Run traceroute or tracert to a website and count how many hops your data takes.
    4. Write 2-3 sentences explaining what the browser padlock guarantees, and what it does not guarantee.
